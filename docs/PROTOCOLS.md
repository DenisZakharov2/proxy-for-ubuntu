# Протоколы

Реализация каждого исходящего протокола: что именно сделано, где проверено
и что не поддерживается. Общий интерфейс — трейт
`engine::outbound::Outbound` (`app/src-tauri/src/engine/outbound/mod.rs`).

## Сводка

| Протокол | Статус | UDP | Проверка на живом сервере |
|---|:--:|:--:|---|
| `direct` | рабочий | ✅ | не требуется |
| `http` | рабочий | ❌ | синтетический сервер |
| `socks5` / `socks5h` | рабочий | ✅ | синтетический сервер |
| `shadowsocks` | рабочий | ✅ | синтетический сервер |
| `trojan` | рабочий | ❌ | нет |
| `vless` | ⚠ не проверен | ✅ | **нет** |
| `vmess` | ⚠ не проверен | ✅ | **нет** |
| `ssh` | рабочий | ❌ | локальный OpenSSH |

Статус «синтетический сервер» означает: в тестах поднимается настоящий
сервер соответствующего протокола на loopback и через него гоняется реальный
обмен байтами. Это ловит ошибки формата, но не ошибки совместимости с
конкретной реализацией на другой стороне.

---

## direct

`engine/outbound/direct.rs`. Прямое соединение до настоящего получателя.
**Ограничения:** разрешает только адреса; домен резолвится локально через
системный резолвер (`getaddrinfo`), с перебором всех A/AAAA до первого
успешного соединения. Это осознанный компромисс: если первый адрес недоступен
(например, AAAA без маршрута), соединение не откатывается сразу.

---

## http

`engine/outbound/http.rs`. Метод CONNECT по RFC 7231 §4.3.6.

**Что поддержано:** CONNECT, Basic-аутентификация, `password_file` вместо
пароля в конфиге, разбор кода ответа в человекочитаемые сообщения
(407 → «требует логин и пароль», 502/503/504 → «прокси не смог связаться»).

**Что нет:** обычные GET/POST через прокси, проксирование UDP. Для прозрачного
перехвата это не нужно: приложение уже сформировало запрос на прямую цель,
и прокси требуется только для туннеля.

**Безопасность.** Домен в заголовке `CONNECT` проверяется на отсутствие
пробелов и непечатных символов. Без этой проверки имя вида
`evil.com HTTP/1.1\r\nX: y` позволило бы дописать в запрос произвольные
заголовки. Есть тест `rejects_header_injection_in_hostname`.

## socks5 / socks5h

`engine/outbound/socks5.rs`. RFC 1928 плюс UDP ASSOCIATE (RFC 1928 §7).

Разница только в одном поле: `remote_dns: true` (он же тип `socks5h`) передаёт
домен прокси как домен, `false` резолвит его локально. Первый не течёт DNS,
второй быстрее, но список посещённых доменов виден вашему провайдеру.
**По умолчанию — первый.**

Аутентификация: без неё и username/password. Метод, которого прокси не
поддерживает, даёт внятную ошибку с кодом, а не «соединение не удалось».

**UDP ASSOCIATE.** Прокси часто возвращает `0.0.0.0` вместо своего адреса —
тогда используется адрес самого SOCKS-сервера. TCP-соединение ассоциации
удерживается живым всё время: многие серверы закрывают UDP-канал, как только
ассоциированный сокет отваливается.

## shadowsocks

`engine/outbound/shadowsocks.rs`. AEAD-режим по SIP004.

**Шифры:** `chacha20-ietf-poly1305`, `aes-128-gcm`, `aes-256-gcm`. Legacy-шифры
(`aes-*-cfb`, `chacha20`, `rc4-md5`) в конфиге принимаются, но помечаются в UI
как небезопасные: без AEAD злоумышленник в середине пути может менять данные,
оставаясь невидимым.

**Формат кадра (частая ошибка реализаций):**

```
[длина шифротекста: 2 байта][шифротекст]
```

где **длина полезной нагрузки лежит внутри шифротекста** — это первые два
байта открытого текста. На проводе заголовок кадра — ровно 2 байта, а тег
AEAD приезжает в конце блока. Перепутать эти два поля — самая частая причина
«вроде всё настроено, но ничего не работает».

**Ключи.** Мастер-ключ берётся как есть, если это base64 нужной длины, иначе
пароль растягивается по EVP_BytesToKey с MD5 — так же, как это делает
оригинальный shadowsocks. Подключевой ключ выводится через HKDF-SHA1 из
мастер-ключа и соли конкретного соединения, поэтому один ключ безопасно
использовать на разных соединениях.

**Nonce** — 12 байт, little-endian счётчик, общий для всех чанков направления.
Тест `nonce_increments_little_endian_with_carry` проверяет перенос.

## trojan

`engine/outbound/trojan.rs`. Схема trojango/go-trojan.

**Формат:** `CMD(1), ADDR, CRLF, payload, SHA224(password)_hex, CRLF`.

Отличие от SOCKS5 — пароль проверяется **на каждом пакете**, а не один раз на
рукопожатии. Это защищает от подмены данных внутри TLS: клиент видит, что
подпись ответа не сошлась, и рвёт соединение.

**TLS:** через `rustls` с системными корнями из `webpki-roots` (не зависит от
наличия пакета `ca-certificates` в системе). ALPN: `h2`, `http/1.1`.
`skip_cert_verify` оставлен в конфиге, но при каждом соединении пишет
предупреждение в журнал — пользователь должен видеть, что проверка отключена.

**Ограничения:** UDP не реализован. Протокол требует отдельного согласования
UDP-сессии, а недоделанный QUIC-туннель хуже прямого соединения. При попытке
движок получает ошибку с указанием, что делать: добавить outbound SOCKS5h с
`udp: true` и направить на него правило `NETWORK,udp`.

## vless

`engine/outbound/vless.rs`. ⚠ **Не проверен против живого Xray-сервера.**

**Формат запроса:** `ver(1)=0, uuid(16), addonsLen(1)=0, cmd(1), port(2), atyp(1), addr, payload`.

**Важно:** типы адресов здесь свои, не как в SOCKS5 — `0x01` IPv4, `0x02` домен
с префиксом длины, `0x03` IPv6. Путать их — типовая ошибка, из-за которой
соединение молча не работает. Есть тест `address_types_differ_from_socks5`.

**Транспорты:** `tcp` (сырой) и `ws` (WebSocket поверх HTTP Upgrade). Для `ws`
TLS включается автоматически: сервер без TLS для WebSocket почти всегда означает
«забыли включить».

**WebSocket.** Собственная минимальная обёртка: маскирование исходящих кадров,
размаскирование входящих, склейка фрагментов, обработка ping/pong/close.
Кадры больше 1 МиБ отклоняются.

**Что не поддерживается:**
- `flow` (XTLS / Reality) — конфиг с непустым `flow` отвергается на этапе
  валидации, а не игнорируется молча. Reality требует не TLS, а особого
  криптографического хендшейка с серверным ключом;
- gRPC-транспорт;
- Reality/XTLS.

**Почему статус ⚠.** Код написан по спецификации и покрыт тестами на
собственных серверах, но не соединялся с настоящим Xray. Если проверите —
пришлите лог, это снимет вопрос у всех остальных.

## vmess

`engine/outbound/vmess.rs`. ⚠ **Не проверен против живого Xray-сервера.**

Только AEAD-режим (Xray-core 1.8+), только `alterId: 0`. Старый MD5-режим
несовместим с AEAD, и конфиг с ненулевым `alterId` отвергается при валидации.

**Формат запроса** (все целые — big-endian):

```
authID   = AES-128-ECB(uuid, PKCS7(timestamp[8]), zero-iv)          → 16 байт
lenBuf   = AES-128-ECB(authID, PKCS7([len(nonce)+len(payload)+4]), zero-iv)[:2]
nonce    = random(12)
lenPlain = [len(payload)][2]
crc32    = CRC32(nonce ‖ lenPlain ‖ payload)
header   = authID ‖ lenBuf ‖ nonce ‖ AEAD(authID, nonce, lenPlain ‖ payload ‖ crc32, aad=lenBuf)
```

`payload` — это блок VMess: `cmd(1), port(2), atyp(1), addr, данные`.
Обратите внимание: `lenPlain` — длина **всего блока**, а не только данных.

**Шифры:** `aes-128-gcm` (по умолчанию) и `chacha20-poly1305`. Ключ всегда
16 байт — это `authID`; для ChaCha20-Poly1305, которому нужен 32-байтный
ключ, `authID` дополняется нулями до 32. Именно так это делает Xray
(`generateChacha20Poly1305Key`).

**Заголовок ответа** разбирается «мягко»: исторически Xray отдавал в этих
18 байтах мусор, поэтому длину берём из последних двух байт блока и не падаем
при несовпадении CRC.

**Что не поддерживается:** `alterId != 0`, старый (не-AEAD) режим, gRPC,
`security: rc4` и прочие устаревшие шифры.

## ssh

`engine/outbound/ssh.rs`. Единственное отступление от правила «с нуля».

Реализация SSH-протокола с обменом ключами, KEX и набором шифров — это годы
работы. Самописная реализация в системном маршрутизаторе была бы источником
уязвимостей, а не преимуществом. Поэтому поднимается локальный SOCKS5 через
системный OpenSSH:

```
ssh -N -D 127.0.0.1:<порт> -o ServerAliveInterval=30 user@host
```

Наш движок (маршрутизация по правилам, учёт трафика, раздельный up/down,
реакция на падение сервера) работает поверх него как обычно — для
пользователя разницы нет.

**Требуется** пакет `openssh-client` (он в зависимостях пакета).

**Ограничения:** только TCP. Вход по паролю возможен лишь при наличии
`sshpass`, которого в зависимостях нет; практический путь — ключ
(`key_file`). Неизвестный ключ хоста принимается в режиме `accept-new`:
интерактивный запрос пароля в фоновом демоне привёл бы к зависанию.

## Общее для всех

**Таймауты.** Каждое соединение с прокси ограничено 10 секундами, каждое
проверочное — 8. Без этого Apply завис бы на мёртвом сервере вместо отката.

**Секреты в логах.** `outbound::describe()` печатает адрес, порт и протокол,
но никогда — пароль, ключ или UUID.

**Ошибки.** Каждая несёт имя протокола (`Error::protocol`), текст для
пользователя и, где уместно, подсказку в `hint()`. Внутренние детали
(например, путь к ключу) в сообщение не попадают.
