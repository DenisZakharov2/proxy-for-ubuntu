# Архитектурное обсуждение: Web UI

Статус: дискуссия перед реализацией (пункт дорожной карты №17). Решение не принято.

## Текущая архитектура

```
GUI (Tauri, пользователь)  ← Unix сокет /run/proxy-for-ubuntu/ctl.sock →  démon (root)
```

Дémon — единственный привилегированный процесс. Держит TUN, nftables, сокеты, правила.
GUI — тонкая обёртка: любая команда уходит по сокету в démon, бизнес-логики на стороне GUI нет.
HTTP-порта у démon нет, и по дорожной карте не должно быть.

## Что требует Web UI (из дорожной карты)

- отдельный непривилегированный процесс;
- существующий IPC-сокет для связи с démonом;
- без HTTP-порта от root.

## Варианты

### Вариант A: Web UI внутри существующего GUI-процесса (Tauri)

Web-интерфейс открывается в том же окне Tauri, что и текущий GUI, через дополнительные страницы/роуты фронтенда. Все запросы ідут в démon по тому же Unix-сокету.

| За | Против |
|---|---|
| Новых процессов не добавляется; IPC уже есть | Не совсем «отдельный процесс» из формулировки дорожной карты; фронтенду придётся обслуживать два интерфейса (нативный GUI + веб) |
| Нет нового поверхности атаки (никакого additional HTTP-сервера) | Веб-UI доступен только когда запущен графический GUI |

### Вариант B: отдельная непривилегированная утилита `pfu-web` (systemd-сервис от пользователя)

Небольшой процесс, запускаемый пользователем через systemd (`User=` без root), слушает HTTP **только на 127.0.0.1** (или Unix-сокет в `$XDG_RUNTIME_DIR`), проксирует запросы в démon через `/run/proxy-for-ubuntu/ctl.sock` и отдаёт статические файлы веб-интерфейса.

| За | Против |
|---|---|
| Полностью соответствует формулировке дорожной карты | Новый процесс, новый код HTTP-сервера под soutient группы `proxy-for-ubuntu` на сокете démon |
| Веб-UI доступен независимо от GUI | Требует обработки авторизации/сессий на уровне сокета (все в группе имеют доступ к сокету démon) |

### Вариант C: Web UI как часть démonа через Unix-сокет + внешний веб-сервер

Дémon отдаёт веб-интерфейс не по HTTP, а по уже существующему Unix-сокету (например, метод IPC `web.page`), а внешний непривилегированный веб-сервер (Caddy/Nginx от пользователя) проксирует в демон.

| За | Против |
|---|--- |
| Демон остаётся без HTTP-порта | Требует modifying démon для отдачи HTML/assets через IPC — это бизнес-логика, не относящаяся к маршрутизации |

## Рекомендация

Вариант B (`pfu-web`, отдельный непривилегированный systemd-сервис от пользователя, HTTP только на 127.0.0.1, Existenz через тот же IPC-сокет, что и GUI) — единственный, который формально удовлетворяет всем трём требованиям дорожной карты同时:

1. отдельный процесс,
2. существующий IPC,
3. нет HTTP от root.

Минимум нового кода: HTTP-сервер на несколько ручек, статика, проксирование JSON-RPC в démon. Демон не меняется.

## Открытые вопросы перед реализацией

1. Авторизация: сокет démon доступен группе `proxy-for-ubuntu` — любой пользователь в группе может отправить `config.apply`. Требуется ли дополнительная проверка в `pfu-web` или достаточно прав на сокет?
2. Куда складывать статику Web UI: `/usr/share/proxy-for-ubuntu/web/` или бандл в бинарник `pfu-web`?
3. Порт: фиксированный (например, 17471) или динамический с записью в `/run/proxy-for-ubuntu/web.port`?
4. Нужен ли Web UI вообще, когда уже есть Tauri GUI? (вкладки duplication)
