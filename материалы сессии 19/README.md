# Сессия 19 — перехват системного резолвера `127.0.0.53`

Что сделано: приложения, которые спрашивают имена через systemd-resolved
(stub `127.0.0.53:53`), больше не ходят мимо прокси. Запрос перехватывается
правилом nat output, разбирается слушателем демона `127.0.0.1:15053`, уходит
вышестоящему DNS из `dns.servers` через outbound, выбранный правилами по
имени, и возвращается приложению от имени `127.0.0.53:53` (источник
восстанавливает conntrack). Работает **без TUN**.

## Файлы стенда

| Файл | Что |
|---|---|
| `dns-stub-stand.sh` | две netns: клиент `pfu-dns` (10.211.0.2) и сервер `pfu-dns-srv` (10.211.0.1, адрес вышестоящего DNS 203.0.113.53) |
| `dns-echo.py` | мини-DNS: A-запись на заданное имя (`-` — на любое), печатает каждый запрос |
| `dns-client.py` | ручной клиент: подключённый UDP-сокет, печатает `rcode`, источник ответа и адреса |

Тест живёт в репозитории: `app/src-tauri/tests/dns_stub_live.rs`
(четыре `#[ignore]`-теста, запускаются только на стенде).

## Как устроен стенд

```
клиентская netns pfu-dns                  серверная netns pfu-dns-srv
┌──────────────────────────────┐          ┌──────────────────────────────┐
│ 127.0.0.53:53  «systemd-     │          │ 203.0.113.53:53              │
│   resolved» → 203.0.113.99   │  veth    │   настоящий вышестоящий DNS  │
│ демон 0.4.0 (тест)           │◄────────►│   → 203.0.113.1              │
│ приложение uid 1000          │10.211.0.x│                              │
└──────────────────────────────┘          └──────────────────────────────┘
```

Ответы разные намеренно: локальная заглушка отвечает `203.0.113.99`, а
настоящий вышестоящий сервер — `203.0.113.1`. Если перехват не сработает,
приложение увидит `.99`, и тест упадёт — «пройти мимо» он не может.

## Запуск

```bash
cd app/src-tauri && cargo test --test dns_stub_live --no-run
# бинарник из target/debug/deps/dns_stub_live-<hash>

docker run -d --privileged --name pfu-stand -v /dev/net/tun:/dev/net/tun \
  -v "$PWD/../..:/src:ro" ubuntu:24.04 sleep infinity
docker exec pfu-stand bash -c 'apt-get update -qq && apt-get install -y -qq iproute2 nftables python3 util-linux'
docker cp target/debug/deps/dns_stub_live-<hash> pfu-stand:/bin/dns_stub_live

docker exec pfu-stand bash -c 'bash "/src/материалы сессии 19/dns-stub-stand.sh" all /bin/dns_stub_live'
```

Разбор по шагам: `setup` | `test <bin>` | `logs` | `teardown`.

## Что показывают тесты

| Тест | Проверяет |
|---|---|
| `stub_query_goes_through_upstream` | приложение получает `203.0.113.1` **от `127.0.0.53:53`**; карта «IP → домен» заполнена; в `breakdown` есть `DIRECT` с ненулевыми байтами |
| `without_stub_the_local_resolver_answers` | при `dns.intercept_stub: false` отвечает локальная заглушка (`203.0.113.99`) — значит, первый тест доказывает именно перехват |
| `rejected_name_returns_servfail` | правило `REJECT` даёт `SERVFAIL` сразу, а не молчание |
| `hijack_dns_answers_locally` | `HIJACK-DNS` отвечает локально (`127.0.0.1` из `/etc/hosts`), запрос наружу не уходит |

не видел, а вышестоящий DNS видел его с адреса клиентской netns.

## Отдельная проверка механизма

До стенда механизм проверялся минимальным опытом (привилегированный
контейнер): nft-правило `meta skuid != 0 ... redirect to :15053`, два
python-слушателя и клиент с подключённым сокетом. Под `uid 1000` ответ
пришёл от `127.0.0.53:53` с адресом прокси-слушателя, под root — от
настоящего «резолвера»: значит, conntrack действительно подменяет источник
ответа обратно, и подключённый сокет приложения датаграмму принимает.

## Ограничения, найденные и записанные

- DNS over TCP к самому резолверу (`127.0.0.53:53/tcp`) остаётся прямым:
  на слушатель перенаправляются только UDP-запросы.
- Если outbound не умеет UDP или молчит 3 с, демон разрешает имя напрямую
  (системный путь, затем DoH) — приложение без DNS не остаётся.
- Порт 53 в `intercept.exclude_ports` отключает и перехват заглушки.
