# Дорожная карта

Документ составлен по замечаниям к версии 0.1.1. Каждый пункт имеет
статус, проверенный по коду, а не по памяти.

Легенда статусов: **готово** — реализовано и работает; **частично** — сделано
не всё, что описано в замечании; **нет** — не начато.

---

## Приоритет 1. Снять главный блокер

### 1. CI с живым Xray — *нет*

Самая дорогая замечание по последствиям: пока ⚠ висит на `vless` и `vmess`,
доверие к проекту держится на слове автора.

Что делаем: workflow `protocols.yml`, который на каждый PR поднимает
Xray в контейнере, генерирует клиентские ключи, прогоняет наш код через
`pfu-cli` и **проверяет реальный обмен байтами**, а не успешность рукопожатия.
Серверная часть (inbound) и клиентская (our outbound) — в одном job.

Что это даст по итогу: либо `vless`/`vmess` переезжают из ⚠ в ✅ с указанием
версии Xray, на которой проверено, либо обнаруживается, что протокол не
совместим, и он честно уходит в ❌ с описанием расхождения. Третий вариант —
«тест проходит, а с настоящим сервером не работает» — исключается конструкцией
теста.

Риск: Xray меняет формат. Закрепить версию образа по digest и обновлять
осознанно.

### 2. Docker — *нет*

**Предлагаю не трогать цепочку `DOCKER-USER`.** Ею владеет Docker: при
обновлении он переписывает правила, и наши изменения либо потеряются, либо
сломают его работу. Вместо этого добавляем собственную цепочку:

```
table inet pfu {
    chain forward { type filter hook forward priority -10; policy accept; ... }
}
```

Приоритет `-10` — раньше `FORWARD` Docker-а (priority 0). Вердикт в нашей
цепочке не разрывающий: пакет помечается и уходит дальше без изменений,
маршрутизацию забирает `ip rule`. Получается то же самое, что и для
локального трафика, но без конфликта.

Переключатель: `intercept.docker: true` (по умолчанию `false` — поведение
не должно меняться молча).

### 3. UDP для Trojan — *нет*

Протокол требует отдельного согласования UDP-сессии, а не «просто отправить
датаграмму». Реализация честная, но нетривиальная.

Побочный эффект, который стоит сказать прямо: даже без Trojan у пользователя
сейчас нет нормального UDP через прокси, кроме SOCKS5-associate и Shadowsocks.
Поэтому работы №2 и №3 стоит делать вместе — иначе «закрыли UDP для Trojan» не
закроет боль «QUIC и игры идут мимо прокси».

## Приоритет 2. Снять барьер входа

### 4. PPA / AUR / COPR — *нет, и не полностью в наших силах*

Создать Launchpad PPA или AUR-репозиторий может только владелец аккаунта,
из агента это сделать нельзя. Что я подготовлю: инструкция, готовые
`debian/`-скрипты публикации и шаблон пакета для AUR.

**Что могу сделать сам:** добавить в README однострочную установку прямо из
GH Releases, чтобы не качать руками:

```bash
sudo apt install ./proxy-for-ubuntu_0.1.1_amd64.deb
```

с указанием, что файл лежит на странице релизов.

### 5. Автосборка — *готово для .deb*

`.deb` собирается в Releases по тегу, проверено: в `v0.1.1` лежат и пакет,
и `.sha256`. **`.rpm` и `.apk` делать не буду:** проект использует
`nftables` и `systemd` особым образом (политическая маршрутизация, `IP_TRANSPARENT`),
и перенос на rpm-based дистрибутив потребует отдельной проверки. Если аудитория
потребует — оформим как отдельную задачу, а не как побочную сборку.

### 6. `pfu-cli config validate --dry-run` — *нет*

Правильная мысль: валидация сейчас доступна только внутри `apply`, а для
CI/CD и Ansible нужна отдельная команда. Стоит немного, польза большая.

Формат как у `nginx -t`: код возврата 0 — всё в порядке, 1 — есть ошибки,
на stdout — список. Без обращения к демону.

### 7. `ExecStartPre=pfu-cli doctor --strict` — *нет*

Сейчас в юните стоит `proxy-for-ubuntud --check`, который проверяет
окружение, но не блокирует запуск при проблемах. Предлагается `--strict`:
ненулевой код возврата, если нет `nftables`, `TUN` или прав.

Осторожно: слишком строгий `ExecStartPre` означает, что демон не поднимется
на машине, где всё работает, но проверка дала ложное отрицание. Проверки
должны быть ровно те, что реально блокируют работу.

## Приоритет 3. Доверие и сообщество

### 8. Матрица совместимости — *частично*

В README есть таблица «протокол → статус», но замечание справедливо: слова
«не проверен» недостаточно. Нужна конкретика вида
«проверено с Xray 1.8.10, с v2ray 5.x не проверялось».

Появится автоматически вместе с №1 — тест сам пишет, с чем он соединялся.

### 9. Шаблон issue для совместимости протоколов — *нет*

Сейчас есть `bug_report.yml` и `feature_request.yml`. Не хватает
`protocol_compatibility.yml`: версия клиента, версия и тип сервера, версия
ядра, вывод `pfu-cli doctor`, лог попытки соединения. Без него баги
`vless`/`vmess` невозможно разбирать.

### 10. Хорошие первые задачи — *нет*

`CONTRIBUTING.md` есть, меток нет. Тестирование `vless`/`vmess` против
живого сервера — идеальная первая задача для новичка: воспроизводится,
результат сразу полезен автору.

### 11. RC → тестирование → stable — *нет*

Справедливо: сейчас тег = релиз, и для программы, которая переписывает
маршрутизацию системы, это рискованно. Предлагается: тег `v0.2.0-rc.1`
собирает prerelease, который держится минимум неделю, `v0.2.0` выходит
после сигнала от тестировщиков.

### 12. Документация на английском — *нет*

`README.en.md` есть, `docs/*.md` только на русском. Ограничивает аудиторию
за пределами СНГ.

Минимум, который стоит сделать: `ARCHITECTURE`, `CONFIG`, `PROTOCOLS`.
Объём — примерно 2000 строк перевода.

## Приоритет 4. Мелкие технические

### 13. `tun.mtu` — *готово, настраивается*

Поле есть, дефолт 9000, задокументировано. PMTU discovery — на стороне ядра,
настраивается через `net.ipv4.tcp_mtu_probing`; в приложении достаточно
одной строки в README, отдельного кода не требуется.

### 14. Reality/XTLS в VLESS — *готово, отказ явный*

Замечание основано на неверной посылке. Сейчас конфиг с `flow: xtls-rprx-vision`
**не проходит валидацию** — пользователь получает ошибку
«требует Reality, которое не поддерживается», а не тихо неработающий прокси.
Это лучше, чем реализация.

### 15. SSH: `known_hosts` и строгая проверка — *нет*

Сейчас жёстко прописано `StrictHostKeyChecking=accept-new`. Для домашней
машины нормально, для корпоративной — дыра: первый запуск принимает любой
ключ.

Предлагаю три режима вместо accept-new по умолчанию:
`strict` (только из known_hosts), `tofu` (принять новый, предупредив в лог),
`accept-new` (текущее поведение). Плюс `known_hosts_file`.

### 16. Экспорт профиля с шифрованием — *нет*

Сейчас есть `redact_secrets` — это маскировка, а не защита: замаскированный
файл бесполезен для применения. Пользователю нужен файл, который можно
безопасно положить в git.

Предлагаю age: `pfu-cli profile export --age` — пароль или получатель
age-ключа. Инструмент один, экосистема зрелая, в Rust есть крейт.

### 17. Web UI для headless — *нет, и здесь нужна осторожность*

Замечание справедливо по сути, но реализация в лоб опасна. HTTP API на
демоне, работающем от root, — это удалённое выполнение кода для любого, кто
достучался до порта. Даже на loopback.

Если делать, то так:
- веб-интерфейс обслуживает **отдельный непривилегированный процесс**;
- он общается с демоном по уже существующему сокету, а не по HTTP;
- наружу не торчит ничего: ни портов, ни новых прав.

Тогда это не новая поверхность атаки, а второй клиент к существующему IPC.
Отдельный трек, требует отдельного обсуждения.

## Не согласен

### 18. Telemetry — *делать не будем*

Предлагается opt-in телеметрия. Не делаю, и вот почему.

Проект позиционируется как инструмент приватности. В README я написал
«нет серверов, телеметрии и аккаунтов». Телеметрия в таком проекте ломает
это обещание, а отзыв «я поставил приватный прокси, а он что-то куда-то
шлёт» бьёт по всей идее. Opt-in здесь не снимает вопрос: люди не читают
то, что не хотят замечать.

**Что закрывает реальную потребность** за пунктом: собрать диагностику и
отправить самому. `pfu-cli doctor --report` печатает анонимный JSON в
терминал, дальше пользователь сам решает, отправлять или нет. Никакого
кода на стороне проекта, никакого канала.

Если аудитория всё же понадобится — правильный способ тот же opt-in
отчёт, без автоматической отправки.

## Чего в замечаниях нет, а стоит

- **Обновление geo-наборов по расписанию.** Сейчас обновление только по кнопке.
  Через месяц наборы устареют, и `GEOIP,cn` начнёт вести себя непредсказуемо.
- **Проверка целостности при обновлении пакета.** При замене бинарника на
  живом демоне старый процесс держит старый код. Нужен reload с сохранением
  состояния.
- **Ограничение скорости и числа соединений.** Для маршрутизатора всего
  трафика это не косметика.
